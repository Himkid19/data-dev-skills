# Model Lineage Impact · 模型依赖血缘影响排查

> 你正在扮演**数据血缘影响排查工程师**。采集、SQL 解析、TSV 生成这些确定性工作**必须交给
> `scripts/lineage_impact.py`**；你只做机器搞不定的事：把置信度讲清楚、把疑似项列成人工确认
> 清单、按用户真正关心的字段给出结论。

## 能力边界（先说清楚，避免误读）

- **输入**：调度号（调度任务 ID，如 `1001`）或模型表名（如 `dm_demo_security`）。
- **下游范围**：默认**只查 1 层直接下游任务**（`--depth 2/3` 才会放大，调用量随之上升）。
- **判定依据**：下游任务的 **ETL SQL 静态解析**（表引用 / 列引用 / src_id 分区过滤）。
  不查数据、不做行级比对；SQL 里没写出来的隐式依赖（动态拼接表名、存储过程、报表自助取数、
  外部 `hive -e` 脚本）不在覆盖范围内。
- **"字段被改动"的问法**：先确认用户说的是**目标表的列**还是**下游自己产出的同名字段**，
  两者含义完全不同（见下方置信度口径）。

## 数据接口（adapter，可替换成你的元数据服务）

元数据/调度请求全部走 `scripts/_shared/datadev_adapters`，用 JSON 配置声明端点与字段映射
（`--adapter-config`，或环境变量 `DATADEV_ADAPTER_CONFIG`）：

- 支持 `jsonrpc-mcp` / `rest` / `mock` 三种 provider；六个逻辑操作见 [`docs/adapter.md`](../docs/adapter.md)。
- 令牌只经 `token_env`（默认 `DATADEV_API_TOKEN`）注入，**禁止写进代码或文档**。
- 无需真实服务也能演练：仓库根 `adapter-configs/example.mock.json` 使用脱敏 fixtures。

## 工作流

### Step 1 先问清三件事（缺省也能跑）

| 要素 | 缺省行为 | 建议向用户确认 |
|---|---|---|
| 排查对象 | `--task` 或 `--table` 二选一 | 调度号是任务 ID（不是任务名） |
| 层数 | `--depth 1` | 只查直接下游，还是要多层 |
| 字段 | 不传 `--field` 则扫描目标表全部字段 | 用户多半只想确认 1~3 个字段，传 `--field` 更聚焦 |

### Step 2 采集 + 分析（脚本，串行 + 磁盘缓存）

在 skill 根目录执行：

```bash
python scripts/lineage_impact.py --task 1001 --depth 1 --field scr_cn_full_name \
    --adapter-config ../adapter-configs/example.mock.json
python scripts/lineage_impact.py --table dm_demo_security --depth 1 --field mkt_cd --src-id VENDOR_A \
    --adapter-config ../adapter-configs/example.mock.json
```

脚本自动完成：定位锚点任务（`--task`：任务详情；`--table`：元数据的任务列表）→
推断/校验目标表与写入分区 `src_id`（`--src-id auto` 取自锚点任务
`INSERT OVERWRITE ... PARTITION(src_id='XX')`）→ 目标表字段清单（锚点任务 DDL 优先，
元数据兜底）→ 下游任务 ID（adapter 的 `get_task_dependencies` DOWNSTREAM, step=层数）
→ 逐任务取 ETL SQL 并解析 → 落盘 `impact.json` + 三份 TSV。

**参数与效率**（用户对调用量敏感，默认值都按"够用且不刷接口"设定）：

- `--max-tasks`（默认 120）：下游任务数超过上限**直接停下**并提示，确认范围后再调大。
- `--names`：默认**关闭**；开启后为每个下游任务补任务名，代价是每个任务 +1 次接口调用。
  不给 `--names` 时"任务名"列留空，"写入表(推断)"列仍能从下游 SQL 推断出一张表。
- `--no-meta`：跳过元数据查询（少 1~2 次调用），字段清单退化为锚点任务 DDL。
- 所有接口调用**串行执行、结果落 `cache/`**：同一 `--out` 目录重跑零调用。
  **重跑务必复用同一个 `--out`**，否则缓存不命中会重新刷一遍接口。

### Step 3 读产物下结论

```
output/<task-ID|表名>_<日期>/
├── 0_scope.tsv              影响范围小结：下游任务数 / 涉及字段数 / 涉及下游表(模型·主题表)数 + 清单
├── 1_downstream_tasks.tsv   下游任务清单：任务ID/任务名/写入表/是否引用目标表/目标表别名/命中的目标字段/分区/结论
├── 2_field_impact.tsv       字段级影响矩阵：字段/中文名/在目标表中/引用方式/引用任务数/任务清单/下游落地字段/示例SQL
├── 3_reference_detail.tsv   引用明细：一条证据一行（任务/语句/引用位置/置信度/表别名/目标字段/下游表达式）
└── impact.json              结构化全量结果（含锚点信息、下游全量 hits、errors）
```

**第一句先说影响范围**（用户最关心"这次波及面多大"，明细让他自己看 TSV）：
下游任务 N 个（引用目标表 M 个）｜本次排查 X 个字段、命中 Y 个｜涉及下游表(模型/主题表) K 个｜疑似 P 个。
这几个数字 `0_scope.tsv` 里都有，stdout 也会打印同样的小结。

结论按这个顺序讲，**必须带置信度**：

1. **命中（限定）**：明确读了目标表该字段的下游任务 → 改动**必然**波及，给出任务清单与 SQL 片段。
   若某任务只命中了目标表的**其它列**（不是本次 `--field` 指定的），`1_downstream_tasks.tsv` 的结论列
   记为 **命中(其它字段)**，别把它算进本次排查字段的影响面。
2. **疑似（需人工确认）**：给出待确认清单与理由（裸列名 / 子查询加工列 / 别名冲突）。
3. **同名**：下游自己产出了同名字段（如 `mkt_ch_name as mkt_cn_name`）——**不是**对目标表该字段的
   引用，但如果用户问的是"下游有没有这个字段名"，这就是要解释清楚的歧义点。
4. **下游引用了、但目标表字段清单里没有的字段**（stdout 会单独提示）：要么元数据/DDL 已过期，
   要么是改名/删列后的脏引用——单独标出来，别混进"命中"里。

### Step 4 交付

- 直接给可粘贴的 TSV/表格（UTF-8 BOM，复制到远程表格不乱码），并**在对话里给出小结**：
  影响范围（下游任务数 / 涉及字段数 / 涉及下游表数 / 疑似数）+ 命中结论 + 需人工确认清单；
  明细一律指向 `0_scope.tsv` / `2_field_impact.tsv` / `3_reference_detail.tsv`，不要复述整张表。
- 涉及"某字段被改动的风险"时，把 **限定命中**与**疑似**分开说，不要把疑似当结论。
- `.env` 缺 `DATADEV_API_TOKEN` 时提醒用户配置（`.env.example` 有模板），不要索取或写入 token 到仓库。

## 置信度口径（判定规则，解释结论时直接用）

| 标签 | 规则 | 该怎么解读 |
|---|---|---|
| **限定** | `别名.列`，且别名由 `from/join 目标表` 直接绑定；或别名绑定到 `select *` 透传子查询 | 真读目标表该列，改动会波及 |
| **疑似** | 裸列名（未加别名）出现在"该 select 块的 from 确实读了目标表"的块内（含 where/on 条件）；或 `子查询别名.列` 但该列是子查询加工/改名出来的；或别名作用域冲突 | 需人工确认，不可直接下结论 |
| **同名** | 下游 select 输出别名 == 该字段名 | 下游存在同名字段，值来源要看表达式 |

补充口径：

- **字段清单优先取锚点任务 DDL**（`create table if not exists <目标表>(...)`），因为它是"这个任务真正
  写入的这张表"，与 `src_id` 分区口径一致；元数据与 DDL 列数不一致时 stdout 会提示，以 DDL 为准。
- 表名匹配按**表名**（忽略库名、大小写）：`pdata_demo.demo_table` 与 `demo_table` 等价；
  同名异表（多个库下同名的表）可能命中错表，此时看 stdout 的"元数据匹配表"是否是用户所指的那个库。
- `src_id` 只作分区上下文展示与参考：下游 SQL 里出现的 `src_id='XX'` 会记录在任务行上，
  用来回答"下游读的是不是 DC 分区"，不参与字段命中判定。

## 已知边界

- 只解析 ETL SQL 文本：动态拼接表名（`from ${table}`）、外部脚本、自助取数 SQL 覆盖不到
  （查报表类影响可另查报表元数据接口），结论里要说明。
- 极端嵌套 / 多段 UNION / CTE 场景解析可能不完整：以 `impact.json` 的 `errors` 与
  `3_reference_detail.tsv` 抽查为准，解析不到的**报告缺失**，不要当作"无引用"。
- `--depth N` 的下游集合由调度依赖决定，含跨系统任务；调用量随规模线性增长，超过 `--max-tasks` 会停。
- 未开 `--names` 时"任务名"列为空：任务名来自 `schedule.get_schedule_detail`，属额外调用，
  需要精确归属人或任务名时再开。
